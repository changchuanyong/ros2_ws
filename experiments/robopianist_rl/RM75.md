# RM75＋L20 接入官方 RoboPianist

首轮交付：双臂双手仿真环境、6,000 步 DroQ 训练、检查点保存与独立进程重载、演奏评估。
工程主线在官方 `robopianist`，机器人模型与 L20 指令映射取自 `ros2_ws/src/ros2_rm_robot/rm_mujoco`。

## 1. 接口规格

| 项 | 值 |
| --- | --- |
| 环境名 | `RoboPianist-debug-RM75TwoNotes-v0` |
| 加载方式 | `suite.load(name, robot="rm75_l20", seed=7)` |
| 动作 | **47 维** = 右臂 7 ＋ 右手 16 通道 ＋ 左臂 7 ＋ 左手 16 通道 ＋ 延音 1 |
| 观测 | **1274 维** = 1226（关节位置/速度、腕部、指尖、琴键状态、`goal` 11×89）＋ 47 上一步动作 ＋ 1 上一步奖励 |
| 物理步长 / 控制周期 | 2 ms / 50 ms（每控制步 25 个子步） |
| 乐谱前瞻 | 10 个控制步 |
| 基座 | `[0.505, ±0.27, 0.0425]`，static5 高肘参考姿态 |
| 坐标变换 | `(x,y,z) = (0.225−old_y, old_x, old_z−0.7175)`；原键顶 0.74 m → 官方 0.0225 m，无缩放 |
| 乐谱 | 代码内合成 2 s：左手 MIDI 55（0.25–0.65 s）、右手 MIDI 72（1.05–1.45 s），40 个控制步 |

L20 的 21 个关节由 16 个有效通道经 `rm75_l20_mapping.py` 驱动，耦合关系与 ROS 源逐字节一致
（SHA256 `ce340ccc…`）。两个拇指通道的协议范围超出 MJCF 限位，已收窄合法指令范围，未改通道归属。

### 探索数据质量问题的定位与修复

最初按规格加了「碰撞/限位即终止」，导致随机预热几乎每步终止：
260 步冒烟里 259 个回合（collision 101、joint_limit 158），平均回合长度 1.01 步，
回放缓冲区几乎全是 `discount=0` 的单步样本，无法学习。

归因探针（`results/collision_source.json`）显示两个独立原因：
臂全范围随机 → 200 步 200 次 `joint_limit`；手指全范围随机 → 撞黑/白键体。

按官方做法改为**不硬终止、违规转奖励惩罚**后，全范围随机探索
5 个回合全部走满 40 步（`results/exploration_after.json`），无需收窄探索范围。
正式训练 150 回合全部走满，证实修复有效。

## 8. 后续训练目标建议

本轮只证明闭环，未证明演奏能力。依据实测结果，下一步优先级：

1. **步数**：6,000 → 至少 100,000 量级再评估 F1，官方为 5,000,000。
2. **碰撞惩罚强度**：训练后 48 条 collision 记录说明 forearm 奖励的 0.5 惩罚不足以约束臂部动作，
   考虑加大权重或引入显式安全项。
3. **指尖碰撞基元**：评估官方 `primitive_fingertip_collisions` 是否降低误触与碰撞。
4. **探索分布**：臂关节全范围随机使限位违规频繁，可评估 READY 附近的课程式探索。

# 第二轮增补（GPU、指法核对、真实谱子、奖励可配置）

## 9. GPU 试验结论

**可用，但端到端收益有限。** 独立环境 `~/robopianist-rm75-gpu-env`，原 CPU 环境未改动。

- Jetson AI Lab 索引（`pypi.jetson-ai-lab.io/jp6/cu126`）**不托管 JAX**：`jaxlib`、`jax-cuda12-plugin`
  均 302 回落到 pypi.org（该索引只对 torch 等提供 Tegra wheel）。
- 但 PyPI 的 `jax-cuda12-pjrt==0.4.35` 与 `jax-cuda12-plugin==0.4.35` 有 **aarch64 / cp310** wheel，
  在 Tegra（sm_87、CUDA 12.6、cuDNN 9.3）上可直接加载，`jax.default_backend()=="gpu"`。
- **必须加 `XLA_FLAGS=--xla_gpu_enable_triton_gemm=false`**。否则 GEMM fusion autotuner 的 kernel
  缺 sm_87 镜像，SIGABRT：`no kernel image is available for execution on the device`。
  基础算子（1024×1024 matmul）本身可用，故只需禁用该 fusion。
- **必须加 `XLA_PYTHON_CLIENT_PREALLOCATE=false`**（官方 `run.sh` 亦有）。JAX 默认预占 75% 显存；
  Jetson 为统一内存，父训练进程预占约 46 GB 后不释放，评估子进程再预占即 OOM
  （`NvMapMemAllocInternalTagged ... error 12`，整机 61 GB 耗尽）。首轮 6000 步帧少侥幸通过，
  452 帧真实谱触发。曾因此中止一次对照运行，不完整产物移存 `twinkle_m0p1_aborted_partial/`。

实测对照（batch 256、obs 1274、action 47、DroQ，排除 JIT，`block_until_ready` 计时）：

| 项 | CPU | GPU | 倍数 |
| --- | --- | --- | --- |
| 隔离单次 `update` | 56.31 ms | 10.03 ms | **5.62×** |
| 真实循环预热后每步（含 `sample_actions`＋传输＋缓冲） | 114.7 ms | 95.1 ms | **1.20×** |
| 6,000 步整轮 | 263.1 s | 238.9 s | 1.10× |
| 环境步进 | 0.0296 s/步 | 0.0287 s/步 | ≈1（CPU 瓶颈） |

**修正一个 earlier 误估**：曾按隔离基准外推端到端 2.17×，那是错的——真实循环每步还有
`sample_actions`、host/device 传输和缓冲区开销。按真实每步成本外推，GPU 端到端约 **1.2×**；
5M 步时环境占 GPU 总耗时约 75%，进一步提速的杠杆是**多环境并行采样**而非更强 GPU。

GPU 整轮验收同样通过：1000 次更新、150 回合全 `score_complete`、独立进程重载
`deterministic_actions_equal=true`、最大绝对误差 0.0。注意 GPU 与 CPU 浮点不同，
回报 −70.55 vs −77.05、轨迹不同；**确定性只在同一后端内保证**，跨后端不保证逐位一致。

GPU 训练命令（在 3.2 基础上换环境并加两个变量）：

```bash

  ~/robopianist-rm75-gpu-env/bin/python -B rm75.py train ...
```

## 10. 指法标注核对（回应 PIG 问题）

**指法机制完整且已启用**，Jetson 实证：

```
has_fingering: True
disable_fingering_reward: False
reward terms: [key_press_reward, sustain_reward, energy_reward, fingering_reward, forearm_reward]
fingering obs shape: (10,)   # 2 手 × 5 指
```

- 用的是距离型 `fingering_reward`，**不是** OT 回退版。
- 合成 2 秒谱的指法是**手写的**：`part=6`→左手食指按 MIDI 55，`part=1`→右手食指按 MIDI 72。
  机制与官方相同，但标注来源不是 PIG。
- 因此 **F1=0 不能用「缺指法先验」解释**；官方消融（去指法先验几乎学不动）不适用于本实现。

## 12. 奖励可配置与 learning-lab 对照

新增两个 CLI 参数（默认保持官方值，不改变既有行为）：

- `--fingering-margin <m>`：指尖-键距离容差。官方 `_FINGER_CLOSE_ENOUGH_TO_KEY=0.01`。
- `--energy-coef <c>`：能耗惩罚系数。官方 `_ENERGY_PENALTY_COEF=5e-3`（本就是构造参数）。

参考 `Lixin-Jing/robopianist-learning-lab` 的 `training_runs/`（PPO、20,224 步、3 种子、不选最佳种子）：

| 组 | 基线 key_micro_f1 | unwanted_pressed | 说明 |
| --- | --- | --- | --- |
| 他们的 original（margin 已=0.1，**10× 官方**） | 0.0103 | 83.7 | 非官方默认 |
| margin 0.3（30× 官方） | 0.0269（+162%） | 119.0 | F1 最好但误触更多 |
| margin 0.5（50× 官方） | 0.0021（−79%） | 123.0 | 过宽反而崩坏 |
| energy 0.001（官方 1/5） | 0.0062 | 57.0 | 误触最少、回报最高、F1 较低 |

两点结论：他们的基线 F1 也只有 1–2%，与本实现 0% 同量级，低 F1 是任务常态；
**官方 1 cm 指尖容差对 RM75＋L20 可能过紧**，shaping 信号弱，是除步数外的真实候选因素。

| margin 0.1 | **第 5001 步崩溃**（首策略动作） | — | — | — | — | `mjWARN_BADQACC` |
| margin 0.3 | 20000 步 / 15000 更新 / 44 回合全走满 | 0 | 17 | 34/34 | −401.9 | **258** / 39 |

两个完成组的重载校验均通过（独立进程、确定性动作误差 0.0、actor_step 15000）。

### 哪组更好与基线选择

**三组都不会弹**（F1 全 0、34 音全漏），故「好」只能按其他标准分：

| 标准 | 最优 | 说明 |
| --- | --- | --- |
| 能否演奏（F1） | 平局，均 0 | 20,000 步均不足 |
| 回合回报 | margin 0.3（−401.9） | 系指尖接近奖励变宽松所致，**非演奏能力** |
| 误触帧 | **官方 0.01**（4） | margin 0.3 为 17 |
| 碰撞数 | **官方 0.01**（105） | margin 0.3 为 258，翻倍以上 |
| 训练稳定性 | 官方 0.01 / 0.3 | margin 0.1 首策略步崩溃，不可用 |

**继续训练的基线选官方 margin 0.01。** 0.3 的高回报是 shaping 奖励宽松的假象，
代价是碰撞翻倍、误触增多；对真实机械臂而言碰撞是硬伤，比回报数字重要。
0.01 物理行为最干净，是最安全起点；0.1 直接排除。

**结论：不采纳单独放宽 margin。**
- margin 0.1 在首策略步即物理失稳，实测 critic_loss 1.3e6、entropy −1191 后出现 BADQACC；
  但官方组与 0.3 组首步 critic_loss 也分别约 1.319e6、1.318e6，因此大首步损失不是 0.1 独有，
  不能据此认定「margin→大 loss→崩溃」的确定因果。当前结论仅是**该配置在 seed 7 首策略步失稳**，
  具体根因待查；若以后重试宽 margin，仍须配合能耗项、梯度裁剪与短程稳定性预检。
- margin 0.3 回报改善（−401.9 vs −715.6，因指尖接近奖励有了信号），但**碰撞翻倍以上
  （258 vs 105）、误触增多（17 vs 4）**，F1 仍 0、34 音全漏。与 learning-lab「margin 0.3
  F1 最好但误触更多」的权衡一致，且在带机械臂的本任务上碰撞代价更大。
- 20,000 步／15,000 更新在 451 步真实长谱上仍不足以产生演奏能力；主导瓶颈是**步数**与
  **碰撞/安全约束**，不是指尖容差。

下一轮建议（按优先级）：
1. 步数提到 100,000+ 再评 F1。
2. 加大碰撞/安全惩罚或引入显式安全项（当前 forearm 0.5 不足以约束臂部）。
3. 若要放宽 margin，同时把 energy 系数降到 ~0.001 并考虑梯度裁剪，先做短程稳定性预检。
4. 多环境并行采样摊薄 CPU 环境瓶颈（GPU 端到端仅 1.2× 的主因）。

产物：`results/twinkle_official/`、`results/twinkle_m0p1/`（崩溃现场）、`results/twinkle_m0p3/`
及对应 `.log`；OOM 中止的不完整产物在 Jetson `twinkle_m0p1_aborted_partial/`。

测试：集成测试 **54 passed**（新增指尖容差单调性、能耗系数可配置、真实谱子加载带指法三项）。

### 13.2 为什么那么做（决策理由）

1. **训练不因碰撞/限位硬终止**：官方 RoboPianist 本就不做碰撞终止。最初按字面加了硬终止，
   结果随机预热几乎每步终止（260 步里 259 回合、平均 1.01 步），回放缓冲全是 `discount=0`
   的单步样本，无法学习。改为官方式「违规计入 forearm 奖励惩罚＋去重写入评估记录」后，
   全范围随机 5 回合全部走满 40 步。**因此也放弃了原先「收窄探索范围」的补丁**——不再需要。
2. **补 discount 0.8 与 `action_reward_observation`**：官方 `run.sh` 用 discount 0.8（不是
   默认 0.99）并开启 action/reward 进观测；漏传会偏离官方配方。观测因此 1226→1274。
3. **首轮用 CPU、之后才试 GPU**：用户规格明确优先 JAX CPU 后端，且 6000 步 CPU 仅 4.4 分钟。
   为评估规模化才做 GPU 试验；实测端到端仅 1.20×（环境是 CPU 瓶颈），故 GPU 是可选加速而非必需。
4. **GPU 必须带两个 XLA 变量**：`--xla_gpu_enable_triton_gemm=false` 因 SBSA wheel 的 fusion
   kernel 缺 sm_87 镜像（否则 SIGABRT）；`XLA_PYTHON_CLIENT_PREALLOCATE=false` 因 Jetson 统一
   内存下 JAX 默认预占 75% 显存，父训练进程不释放导致评估子进程 OOM（曾中止一次对照）。
5. **做 margin  sweep 的动机**：learning-lab 的「original」基线 margin 已是官方 10 倍、0.3 最好，
   怀疑官方 1 cm 指尖容差对 RM75＋L20 过紧、shaping 信号弱。实测后**否定单独放宽**（见 12 节）。
6. **基线选官方 margin 0.01**：三组 F1 均 0；0.01 误触与碰撞最少、物理最干净；0.3 的高回报是
   shaping 宽松的假象且碰撞翻倍；0.1 首策略步崩溃。对真实机械臂碰撞是硬伤，故选最干净者。
7. **加真实谱子**：合成 2 秒谱只验证数据流；真实谱（Rousseau Twinkle/Nocturne）自带 PIG 指法，
   才能评估演奏。用户明确要求加入。
8. **指法走 `note.part` 字段**：官方 `has_fingering()` 读 protobuf 的 `part`，经 note_seq
   pianoroll 变成 `PianoNote.fingering`（右手 0–4、左手 5–9）。合成谱手写 `part=1/6`＝双手食指；
   机制与官方相同但标注来源非 PIG，故 F1=0 不能归因于缺指法先验。
9. **L20 两个拇指通道收窄合法指令**：导入映射的协议范围超出 MJCF 关节限位；保留通道归属与
   耦合关系不变，只收窄合法命令区间，避免越限。
10. **碰撞检查覆盖双臂全部几何但排除 L20 内部装配**：掌壳为单一非凸 CAD，其凸包与内部手指
    机构天然重叠；仅排除 L20 内部 body 对，保留臂-臂、手-手、机器人-琴键/桌面检查。

## 14. safety 配对（T-0043）与 100k 长训配置

在真实 Twinkle 上跑 safety_penalty 0／0.5／1.0 各 20,000 步（种子 7、DroQ、GPU、
带 PhysicsError 防护），预热后每步违规率与模型安全性：

| safety | 预热后碰撞/步 | 预热后限位/步 | 最终 F1/误触 | 最终违规(coll+jl) | 最佳 F1/误触 | 最佳违规(coll+jl) |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | 0.740 | 0.916 | 0 / 0 | 74+23 | 0.0165 / 185 | 1598+1296 |
| 0.5 | 0.666 | 0.916 | 0 / 0 | 158+88 | 0.0233 / 215 | 1599+1259 |
| 1.0 | **0.638** | 0.919 | 0 / 0 | **48+26** | **0.0419 / 126** | 1716+1269 |

**结论：**
- safety 1.0 为三者最优（最终模型最干净、最佳 F1 最高、误触较少），但改善幅度有限
  （碰撞率仅 ↓14%），限位率几乎不变。
- **安全惩罚量级不足**：forearm 安全项 ≤1.0/步，而能量项 −几十~−几百/步，差两个数量级，
  策略"感觉不到"安全惩罚。单纯加大 safety_penalty 不是有效杠杆。
- 不开安全门槛时，"最佳"模型恒为高 F1 高碰撞的不安全模型（~1600 碰撞）。

**100k 长训配置**（据此选定，已启动）：
`--safety-penalty 1.0 --energy-coef 0.001 --max-collision-frames 0 --max-joint-limit-frames 0`
＋ `--checkpoint-interval 10000 --eval-interval 10000`。
- energy 降 5 倍（0.005→0.001，learning-lab round-3 做法）让安全项相对变强；
- 选模开安全门槛 0。注意门槛是**优先安全而非硬拒**：`evaluation_rank` 首元素为 safe 标志，
  首个评估即使不安全也会先成为 best，之后仅更安全者可替换；若始终无安全评估，best 为
  "最不坏"的不安全模型。因此 best_checkpoint 不保证安全，须结合 `best_evaluation.json` 判读。

**100k 结果**（safety 1.0 + energy 0.001 + 门槛 0，已完成）：
- 100,000 步／95,000 更新／0 次物理失稳；预热后碰撞 **0.499/步**（基线 0.74）、限位 0.962/步（未降）。
- 最终评估 F1=0、onset=0、误触 7、回报 **+12.7（转正）**、违规 69+36；best F1=0（collF 3/jlF 3）。
- 重载误差 0.0。
- **结论：学会"安静避碰"（碰撞↓、回报转正），但仍未学会按对音（onset 恒 0）。**
  瓶颈不在步数，而在探索/可达与动作范围——支持转向单音可达初始化＋受限探索课程。

产物：`results/twinkle_s0/`、`twinkle_s05/`、`twinkle_s10/`、`twinkle_100k/` 及 `.log`。

## 14. 已实现的训练调整

本节记录 2026-11-12 用户确认后的代码改动；**Windows 仅完成 AST 与 diff 静态检查，
Jetson 集成测试、短配对和长训均待执行，不能把本节写成仿真通过。**

### 14.1 乐谱窗口与空白处理

`rm75.py` 新增：

- `--trim-silence / --no-trim-silence`：训练入口默认开启，与官方 `run.sh` 对齐；
  任务类自身默认仍关闭，旧集成测试和直接 `suite.load` 行为不变。
- `--initial-buffer-time 0.5`：去空白后保留 10 个控制步准备时间。
- `--trailing-silence 0.5`：显式保留 10 个控制步用于末尾松键评估。
- `--note-offset` 与 `--note-limit`：按 `(start_time, end_time, pitch, part)` 排序后截取课程窗口；
  省略 `note-limit` 即完整乐谱。空窗口和非法参数直接报错。

Twinkle 不再把前约 294 个无目标音控制步放进每个训练回合。初始缓冲会计入评估的期望 onset 帧，
不会把 0.5 秒准备时间误判为提前按键。

### 14.2 显式安全惩罚与安全指标

任务新增 `safety_penalty`，训练入口对应 `--safety-penalty`：

```text
无碰撞或限位违规：forearm_reward = +0.5
存在违规：        forearm_reward = -safety_penalty
```

每个控制步至多影响一次奖励，不按 25 个物理子步重复累加；仍然**不因违规硬终止**。
任务类默认值为 0，保持前两轮行为；新配对实验显式比较 0、0.5、1.0。

新增指标：

- `collision_frames`、`joint_limit_frames`：出现对应违规的控制步数，不再只依赖去重接触对数；
- `max_penetration_m`：本回合最大碰撞穿透；
- `reward_components`：key、sustain、energy、fingering、forearm 各分量回报；
- 音符级 `onset_hit`、`onset_error_seconds`，以及 `onset_recall`、`onset_mae_seconds`；
  默认 onset 容差为 1 个控制步，可用 `--onset-tolerance-steps` 修改。

原 `violation_counts` 继续保留，含义仍是**按接触对/关节组合去重的记录数**，不能当作碰撞帧数。

### 14.3 周期评估、最佳模型与恢复

默认每 5,000 步保存检查点，每 10,000 步以固定 `--eval-seed 1007` 做确定性评估。
周期评估不渲染视频，最终独立进程评估仍输出完整视频。新增产物：

```text
checkpoint.msgpack                 最新完整 agent
resume_state.pkl                   replay、RNG、步数、回合与安全累计状态
reload_probe.npz                   最新重载探针
checkpoints/step_XXXXXXX/          各周期 agent 与重载探针
evaluations/step_XXXXXXX/          周期指标、逐帧 rollout、MIDI 事件与排序
best_checkpoint.msgpack            最佳评估 agent
best_reload_probe.npz              最佳模型重载探针
best_evaluation.json               最佳模型指标
best_checkpoint.json               最佳步数与排序值
```

最佳模型先应用可选安全门槛 `--max-collision-frames`、`--max-joint-limit-frames`，
再按 F1、onset recall、碰撞帧、限位帧、误触帧排序；不跨奖励配置比较总回报。
`evaluate --best` 可在全新进程中重载最佳模型。

恢复训练：

```bash
cd "$RM75_RL_DIR"
~/robopianist-rm75-env/bin/python -B rm75.py train \
  --output ~/robopianist-rm75-results/twinkle_long_safe0p5 \
  --resume ~/robopianist-rm75-results/twinkle_long_safe0p5 \
  --steps 100000
```

`--steps` 是总目标步数，不是追加步数。恢复会还原 agent、优化器、replay、两个 NumPy RNG、
更新/回合计数与训练秒数，并**从新回合开始**，不声称逐位接续崩溃前的物理回合。
`resume_state.pkl` 使用 pickle，只能加载自己生成且可信的检查点。
replay 容量在首次运行时按 `--steps` 确定；计划做 10 万步时应首次就以 `--steps 100000` 创建，
之后用同一目标恢复，避免从 2 万步实验恢复后仍只有 2 万容量而影响长训对照。
